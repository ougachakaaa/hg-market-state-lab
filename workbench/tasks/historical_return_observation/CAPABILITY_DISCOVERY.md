# G3 Capability Discovery contract

This specializes [Task version 1](task.json), its prospective G3 criteria and the
shared [Gate](../../contracts/GATE.md) contract. The [WB-03 user Goal](DISCOVERY_REQUEST.md) explicitly
authorizes implementation of this already approved discovery slice. Version 1 and
existing Run snapshots remain byte-for-byte unchanged: WB-02 implementation-state
statements in that snapshot describe WB-02, not a permanent prohibition on G3.
WB-04 subsequently adds [G4 planning](WORKFLOW_PLANNING.md); G5 remains unimplemented.
Research owns capability meaning and publication under
[its contract](../../../market_research/descriptive/RESEARCH_CAPABILITY.md);
[HTTP authority](../../../ui_http/products/research/http-contract.md) owns transport.

## Prerequisites and outcomes

`record_g3.py --run RUN_ID` reads an existing, integrity-verified Run of the exact
canonical Task version 1. It never creates a Run or changes its manifest, inputs,
Task snapshot, workflow or previous records. Unsupported snapshots are rejected.
The latest G1 outcome must be PASS with same-Run preserved G1 checker JSON showing
`compatible_openapi`, HTTP 200 JSON, the four compatible operations and no issues.
Discovery uses that evidence's normalized target; a PASS for another origin cannot
authorize discovery here. The latest G2 must be SKIPPED with the explicit existing
MVP deferral reason: `Authentication deferred in current MVP; loopback backend has
no authentication.` No authentication is inferred. Missing, failed, or unsuitable
G1/G2 evidence prevents HTTP requests and produces BLOCKED. Latest attempts govern;
an older PASS cannot hide a subsequent failure.

| Outcome | Meaning |
| --- | --- |
| PASS | Actual list and every detail are valid and consistent; required `trailing_cumulative_return_v1` is published as supported; same-Run evidence saved and verified |
| FAIL | Discovery attempted but a response/transport/identity/content check fails, or successful discovery lacks the Task's required capability |
| BLOCKED | Required G1/G2 evidence or valid finite timeout is absent; discovery not attempted |
| SKIPPED | Not emitted: this Task authorizes deferral only for G2/G6 |

An empty valid list has `discovery_complete=true`, count 0, `task_readiness=false`
and an explicit missing requirement; G3 is FAIL. Other valid catalogs lacking the
required ID behave likewise. Count and IDs always come from the actual list, never
a one-capability expectation. Other published capabilities are inspected too.
No missing entry is synthesized. PASS means publication support, never live market
readiness, full Task completion or long-history executability.

## Read-only inspection and transport validation

`check_capabilities.py` requests GET `/research/capabilities`, followed by one GET
`/research/capabilities/{id}` per returned distinct, nonempty routable ID in list
order. It attempts all details after a valid list, retaining individual failures.
Duplicate/unsafe IDs invalidate the list and prevent detail requests. No OpenAPI,
Preview, Execute, provider, data acquisition or cache operation is invoked by G3.

Use the existing root httpx and Pydantic runtime. Validate strict finite JSON with
duplicate-key rejection, then validate JSON against the exact public
`CapabilityDescription` return type used by both HTTP endpoints, with strict
Pydantic TypeAdapters (list cardinality is unrestricted). This imports a published
type, never calls the Python catalog, scans source or compares against a local
capability inventory. Explicit boolean-type checks close Pydantic Literal's numeric
coercion for the two boolean constants. No financial or Statistics input validator
is duplicated. Unknown JSON properties remain as permitted by the published schema
and are preserved and included in full list/detail equality comparisons. Tests
verify this binding against the actual composed OpenAPI response schemas.

Each detail must match its requested/list ID and the entire list descriptor,
including descriptions, constraints and additional properties. Only actual detail
responses populate `capabilities`; list observations remain separately inspectable.
`task_readiness=true` requires complete valid discovery and the required supported
ID. Every descriptor retains `live_readiness=not_probed`.

## Evidence, limits and stable formatting

The stable schema-version-1 JSON result includes Task/Gate identity, target,
timeout, prerequisite record/evidence references, status/reason code/reason,
actual count/IDs, inspected descriptors, missing requirements and ordered exchange
observations/errors. No timestamps, random IDs, elapsed timings or raw exception
text are generated by the checker. Run IDs/timestamps belong to storage.

Each exchange preserves method/path, HTTP status, content type/encoding, exact
received body bytes as base64, byte count/SHA-256, completion flag and finite error
codes. Both successful and failed responses are retained; malformed JSON is not
replaced by a reconstructed body. Headers other than media/encoding are omitted.
No credentials, proxy environment or exception diagnostics are copied. These
published read-only endpoints must not return private material.

Timeout is finite, > 0 and <= 30 seconds, default 2, **per request**. An overall
per-request caller deadline bounds DNS/headers/slow bodies as well as httpx socket
timeouts. A daemon worker may finish read-only I/O later; it cannot change the
returned snapshot or persist evidence. Partial received bytes are captured at the
deadline. There are no retries or redirects; environment proxies are ignored.
Each response is bounded at 4 MiB; oversize evidence retains the bounded prefix and
explicit incomplete/oversize indication. Non-identity Content-Encoding fails
explicitly rather than interpreting encoded bytes as JSON. Total request count is
one plus the observed valid catalog count; no permanent count assumption exists.

The recorder first registers the complete JSON as an immutable artifact, then
appends G3 citing it. A new RunStore instance reads back and checks the artifact,
outcome, unchanged manifest and existing record prefix after temporary source
removal. Rechecks append independent evidence/outcomes. Storage errors exit nonzero;
partial publication remains governed by the unchanged storage contract. A Run that
changed during inspection is rejected before publication; this is not a distributed
transaction or authorization service. No generic storage gap was found.

CLI prints one report JSON; PASS=0, FAIL=1, BLOCKED=2. Argument errors exit 2;
unsupported/corrupt Run or storage failures exit 1 with a safe error category.
Usage is in [README](README.md); actual WB-03 evidence is recorded separately in
[discovery acceptance](DISCOVERY_ACCEPTANCE.md).
